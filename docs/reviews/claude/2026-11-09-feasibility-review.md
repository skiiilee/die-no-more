## 2. 차단 요소 상세

### 2.1 외부 API 라이선스·비용 (문서 04의 "Pending verification" 항목)

- Pl@ntNet, Kindwise(plant.id / plant.health), Perenual, OpenAI 각각에 대해 확인해야 할 항목:
  - 상업적 사용 허용 여부와 개인 프로젝트 무료 티어 조건
  - 응답 데이터의 캐싱·재배포 허용 범위
  - 월 할당량, 호출당 비용, 초과 시 동작
  - 사용자 사진의 외부 전송·보관 조건 (데이터 보관 정책)
- **특히 Perenual 등 종 관리 정보 데이터는 캐싱 제한이 있을 가능성이 높다.** `species_care`를 캐시 테이블로 설계하기 전에 라이선스를 확인해야 한다.
- 권고: 구현 전에 `docs/reviews/`에 "프로바이더 검증 표"를 만든다 (제공사, 무료 한도, 캐싱 허용, 사진 보관 조건, 확인 날짜, 출처 URL).

### 2.2 사진 업로드 경로

Next.js Route Handler로 원본 사진을 그대로 받으면 두 가지 문제가 생긴다.

1. **요청 본문 크기 제한:** Vercel 서버리스 함수는 요청 본문 크기에 제한이 있다 (대략 4.5MB 수준으로 알려져 있으나 플랜·버전별 확인 필요). 스마트폰 원본 사진은 이를 쉽게 넘는다.
2. **EXIF 위치 정보:** `01-requirements.md`의 "기본적으로 EXIF 위치 정보 제거" 요구사항을 만족하려면 제거 시점을 정해야 한다.

**권고 설계:**
- 클라이언트(브라우저)에서 Canvas로 리사이즈·재인코딩한다. 재인코딩 과정에서 EXIF가 함께 제거된다.
- 원본 전송이 필요하면 Supabase Storage **Signed Upload URL**로 클라이언트가 직접 업로드하고, 서버는 메타데이터만 받는다. 이 경우 서버 측 EXIF 제거 단계가 추가로 필요하다.
- 서버에서 파일 타입은 매직 바이트로 검증한다 (확장자만 믿지 않는다).

### 2.3 장시간 외부 API 호출의 비동기 처리

- 식별·건강 분석 호출은 수 초에서 수십 초가 걸릴 수 있고, 실패·재시도가 발생한다.
- `04-api-design.md`의 `GET /api/identifications/:id`와 `POST /api/plants/:id/analyses`는 이미 비동기 상태 모델을 전제하고 있다.
- **권고:** 처음부터 작업(job) 테이블과 상태 머신(`queued / processing / completed / failed`)을 두고, 클라이언트는 폴링한다. 서버리스 함수 실행 시간 제한 안에 외부 호출을 끝내려고 하지 않는다.
- 외부 호출 실패 시 업로드된 사진은 보존하고 재시도 가능해야 한다 (`01-requirements.md` 인수 시나리오 6번).

### 2.4 한국어 종 데이터 커버리지

- UI는 한국어인데, 식별 API와 케어 데이터 대부분이 학명·영문명 중심일 가능성이 높다.
- 한국어 일반명(예: 몬스테라, 스투키)을 어디서 가져올지 정해야 한다. 수작업 시드 데이터를 쓸지, 공급자 데이터를 쓸지 결정이 필요하다.
- **권고:** MVP는 "식별 후보의 학명 표시 + 한국어 명칭은 가능한 범위에서 표시 + 없으면 학명 사용"으로 정하고, 수동 검색(F04)도 학명 검색을 함께 지원한다.

## 3. 범위 축소 권고

### 3.1 건강 분석(F05)은 1차 릴리스에서 분리

- 건강 분석은 정확도와 법적 표현 리스크가 가장 큰 기능이다. 문서에도 "진단 아님"이라고 명시되어 있으나, 공급자 정확도가 검증되기 전에는 P0로 두기 어렵다.
- 문서 로드맵상 "Health/history"가 5~6주 차에 들어 있다. 혼자 또는 소규모로 개발한다면 이 기간을 다른 기능에 쓰는 편이 안전하다.
- **권고:** 1차는 "관찰 기록(F09) + 사진 타임라인(F12)"만 구현하고, 건강 분석은 기능 플래그 뒤에 두어 실제 공급자 평가 결과가 나온 뒤 켠다.

### 3.2 P0 기능 수 조정

- P0 기능이 14개이고 화면이 12개다. 12주 로드맵 기준 1인 또는 소규모 개발에는 과하다.
- **권고 MVP 최소 루프:** 인증(F01) → 사진 업로드(F02) → 식별(F03) → 확인·수동 등록(F04) → 식물 CRUD(F06, F07) → 관리 기록(F08) → 할 일(F11) → 앱 내 알림(F13)
- 추천(F10)은 처음에는 결정론적 규칙만 구현하고, LLM 설명은 그 다음 단계로 미룬다.

## 4. 문서 간 표현 정리 요청

### 4.1 "인앱 알림"과 "웹 푸시"의 구분

- `F13 In-app upcoming task notifications`는 **앱이 열려 있을 때만** 보인다. 앱을 닫은 상태의 리마인더는 F14(웹 푸시)에 해당한다.
- 문서상 F13을 P0으로 두면 "리마인더가 온다"로 오해될 수 있다. 문구를 "앱 실행 중 할 일 표시"로 명확히 바꾸길 권한다.

### 4.2 웹 푸시의 플랫폼 제약

- iOS의 웹 푸시는 사용자가 홈 화면에 PWA를 추가한 뒤에만 동작한다 (iOS 16.4 이후 기준, 최신 문서로 재확인 필요).
- F14를 P1로 둔 것은 맞다. 다만 "device compatibility checks"는 구체적으로 어떤 조건을 확인할지 명시가 필요하다 (설치 여부, 권한 상태, 지원 브라우저).

### 4.3 오프라인 범위

- 문서 "Open decisions"의 "어떤 오프라인 작업을 동기화할지"에 대한 Claude 의견은 **MVP에서 오프라인 쓰기는 제외**다.
- 이유: 오프라인 쓰기는 IndexedDB 큐, 멱등성 키, 충돌 해결을 모두 요구하여 구현 비용이 크다.
- MVP의 오프라인은 "마지막으로 본 데이터 읽기 + 오프라인 상태 표시 + 쓰기 시도 시 명확한 실패 안내"로 제한하길 권한다.

## 5. 데이터베이스·보안 설계 검토

### 5.1 원자적 완료 처리

- "할 일 완료 → 관리 기록 생성"은 하나의 DB 트랜잭션이어야 한다. Supabase에서는 PostgreSQL 함수(RPC) 하나로 두 테이블을 함께 쓰는 방식이 가장 단순하다.
- 클라이언트가 보내는 멱등성 키(예: `client_request_id`)를 `care_logs`에 유니크 제약으로 두면 중복 기록을 막을 수 있다.

### 5.2 Service Role 키 주의

- 서버에서 Supabase **service role 키**를 쓰면 RLS가 우회된다. 이 키는 서버 전용이어야 하며, 쓰는 경우에도 모든 Route Handler에서 **소유자 검사를 명시적으로** 해야 한다.
- 권고: 기본은 사용자 세션 기반 클라이언트(RLS 적용)를 쓰고, service role은 배치나 관리 작업으로 한정한다.

### 5.3 Storage

- 사진 버킷은 private, 경로는 `user_id/plant_id/...` 형태로 소유자 기반 정책을 건다.
- 표시는 짧은 수명의 Signed URL을 쓴다.
- 계정 삭제 시 사진 삭제 정책을 DB 삭제와 함께 설계해야 한다 (문서상 "Data lifecycle" 요구사항).

### 5.4 DB 설계 보완

- `identification_sessions.candidates`(JSON)는 원본 공급자 응답을 그대로 저장하지 말고 정규화한 값과 원본 참조를 분리하는 것을 권한다. 공급자 응답 보관 기간은 문서 05의 "Define retention" 항목과 연결된다.
- `care_tasks`의 상태 전이(pending → due → completed/snoozed/skipped/cancelled)는 DB 체크 제약 또는 상태 테이블로 명시하는 것이 좋다.

## 6. 테스트·CI 검토

- 카메라 테스트는 E2E에서 불안정하다. `<input type="file" accept="image/*">`와 고정 샘플 이미지를 쓰는 방식으로 테스트 가능하게 설계하는 것을 권한다.
- 외부 API는 CI에서 실제 호출하지 않고 **어댑터 모킹 + 녹화된 샘플 응답**으로 테스트한다. 실제 호출 테스트는 별도 수동 또는 야간 작업으로 분리한다 (비용 통제).
- CI는 GitHub Actions로 시작한다. Required status checks는 워크플로우가 생긴 뒤 `protect-main` 규칙에 추가한다.
- 배포는 Vercel Preview를 PR마다 사용한다. 운영 배포는 `main` 병합 후에만 수행한다.
